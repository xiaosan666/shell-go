# 设计说明

## 1. 总体结构

```
┌──────────────── 浏览器（Chrome 100+） ────────────────┐
│  index.html + app.js                                  │
│    ├─ secure.js   SM2 / SM4-CBC / HMAC-SM3 信封        │
│    ├─ api.js      握手、登录、加密请求封装              │
│    ├─ terminal.js xterm.js 视图（主题、fit、搜索）      │
│    ├─ files.js    文件浏览与分块上传下载                │
│    ├─ replay.js   会话录制回放播放器                    │
│    └─ app.js      标签/窗格管理、传输层、快捷键、剪贴板   │
└───────────────┬───────────────────────────┬───────────┘
                │ POST（加密 JSON）           │ WS（加密二进制帧）
┌───────────────▼───────────────────────────▼───────────┐
│  Go 服务端（单个二进制）                                │
│    server/    路由、信封解封、会话、限流、静态资源        │
│    auth/      账号、令牌、失败锁定                       │
│    terminal/  PTY 进程、环形缓冲、订阅广播、会话录制     │
│    files/     受限目录读写（路径归一化 + 符号链接校验）   │
│    crypto/    SM2 密钥对、SM4、HMAC-SM3                 │
│    audit/     JSONL 审计                                │
└───────────────────────────────────────────────────────┘
```

进程模型：每个终端一个 `bash -l` 子进程 + 一个 PTY 主端（`/dev/ptmx`）。读协程持续读取 PTY 输出，
写入环形缓冲并广播给订阅者；写操作直接把浏览器发来的字节写入 PTY 主端。

## 2. 关键决策

| 编号 | 决策 | 备选方案 | 理由 |
|---|---|---|---|
| D1 | 持久 PTY，默认 WebSocket，`poll` 可切 | 一次性 `bash -c` | 一次性执行无法保持 `cd`、不支持 `vim/top`、`sudo` 交互会卡死，体验与需求「接近 iTerm」冲突 |
| D2 | 前端免构建，xterm.js 与 sm-crypto 以 vendor 入库 | Vue3 + Vite | 编译机只需 Go，符合「不装 Node」的约束；界面规模不足以支撑工程化收益 |
| D3 | 登录请求单独走 SM2 信封 | 与普通请求复用信封 | 会话密钥必须随首个请求传递，普通信封需要已有密钥，存在先有鸡还是先有蛋的问题 |
| D4 | 标签标题默认 `终端 N`，shell 的 OSC 标题可覆盖 | 固定显示服务名 | 多窗口场景下序号最易区分 |
| D5 | 后台标签缓冲输出，激活时再写入 | 直接写入隐藏终端 | 隐藏容器宽度为 0，xterm 会按极小列数折行，激活后出现错行 |
| D6 | 文件操作限制在 `files.root` 内，路径先 `path.Clean` 再 `EvalSymlinks` | 直接拼接路径 / 只做字符串前缀判断 | 只做字符串判断挡不住 `..` 与指向外部的符号链接；两次校验才能覆盖两种绕过方式 |
| D7 | 录制只存输出，按时间轴写 JSONL | 同时录制输入 / 定时截屏 | shell 会把按键回显到输出流，只存输出即可还原全过程，且体积最小 |
| D8 | 文件上传/下载按 256KB/512KB 分块 | 一次性整文件传 | 加密信封有 base64 膨胀（约为明文 2.4 倍），整传会撞上 4MB 请求体上限 |

## 3. 会话与数据流

### 3.1 登录

```
client                          server
  │  POST /api/handshake  {}      │
  │ ─────────────────────────────►│  生成临时 SM2 密钥对，登记 sid（5 分钟未用即回收）
  │ ◄─────────────────────────────│  { sid, pub, ts, version }
  │                               │
  │ 生成 16 字节会话密钥 K         │
  │ k = SM2(pub, K)               │
  │ POST /api/login {sid,k,data}  │
  │ ─────────────────────────────►│  SM2 解出 K → 用 K 解 data → bcrypt 校验
  │ ◄─────────────────────────────│  { token, expire, transport, ... }（K 加密）
```

### 3.2 终端会话

```
POST /api/term/create   → 返回终端 id、当前缓冲快照、游标
POST /api/term/ticket   → 一次性票据（30 秒）
GET  /ws?ticket=...     → 升级，服务端先推送 {t:"s"} 快照，随后 {t:"o"} 增量
```

- 客户端每个标签对应一个终端 id
- 只关浏览器页面不杀 shell，服务端在 `idle_close` 后才回收
- 缓冲使用绝对偏移游标：`cursor` 表示已消费的字节位置，滚出缓冲时 `reset=true` 触发整屏重放

### 3.3 帧类型

| 方向 | `t` | 含义 | 字段 |
|---|---|---|---|
| S→C | `s` | 快照 | `d`=base64 数据，`c`=游标 |
| S→C | `o` | 输出增量 | `d`=base64 |
| S→C | `e` | shell 已退出 | — |
| S→C | `p` | 心跳 | — |
| S→C | `q` | 心跳回应 | `c`=客户端时间戳，用于测延迟 |
| C→S | `i` | 键盘输入 | `d`=base64 |
| C→S | `r` | 调整尺寸 | `x`=列，`y`=行 |
| C→S | `p` | 心跳请求 | `c`=时间戳 |

## 4. 模块职责

| 包 | 职责 | 关键实现 |
|---|---|---|
| `internal/config` | YAML 装载、默认值、校验 | 自定义 `Duration` 支持 `30m` / `12h` |
| `internal/crypto` | 信封加解密、密钥派生、SM2 密钥对 | `Seal/Open`，`DeriveKeys`：`SM3(K‖0x01)` 取前 16 字节作 SM4 key，`SM3(K‖0x02)` 作 HMAC key |
| `internal/auth` | bcrypt 校验、令牌、锁定 | 令牌 32 字节随机，内存表，空闲/绝对双超时 |
| `internal/terminal` | PTY 生命周期、环形缓冲、订阅广播、会话录制 | 连续落满 256 条消息的订阅者标记 overflow，客户端重连取快照；录制按 `max_mb` 截断并在关闭时去掉空文件 |
| `internal/files` | 受限目录的文件读写 | `resolve()` 归一化路径 + `EvalSymlinks` + 前缀校验；写入校验偏移连续，防止拼接错位 |
| `internal/server` | 路由、信封、静态资源、限流 | 握手限流 60 次/分钟/IP；body 上限 4MB |
| `internal/audit` | JSONL 审计 | 20MB 轮转 |

## 5. 并发与资源

- 每个终端：1 个读协程 + 1 个 WS 写协程 + 1 个 WS 读循环
- 广播使用带缓冲通道（256 条），慢消费者被标记 overflow 并断开，避免拖垮 shell 读取
- 单标签后台输出缓冲上限 1MB，超出丢弃最早数据
- 定期任务（30s）：清理过期会话与票据、回收空闲终端、清理登录失败记录
- 退出时先 `Shutdown` HTTP，再对所有终端发 `SIGHUP`，3 秒后 `SIGKILL`

## 6. 兼容性

- 目标系统：麒麟 V10 / CentOS 7+ / Ubuntu 18.04+，x86_64 与 aarch64
- 纯静态编译，不依赖 glibc 版本；仅需要内核提供 PTY（`/dev/ptmx`）
- 浏览器：Chrome 100+ / Edge 100+ / Firefox 100+（需支持 ES Module、WebSocket、`fetch`）
- 不支持 IE 与 Chromium 86 以下内核

## 7. 待办（后续版本）

## 8. 分屏（v1.2.0 引入，v1.3.0 扩到四宫格）

界面上有三层结构：

```
#terminals
└─ .tabpane（一个标签的容器，data-layout = single | row | col | grid，data-panes = 窗格数）
   ├─ .pane（窗格，各自一个独立终端）
   │  └─ .term-host > .xterm
   └─ .pane（分屏时才存在，最多三个）
```

设计取舍：

| 决策 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 会话粒度 | 一个窗格一个独立 PTY | 同一 PTY 两个视图 | 用户在两栏里执行的是不同命令，共享 PTY 会互相抢输入 |
| 布局方式 | CSS Grid + `data-layout` | 绝对定位手算坐标 | Grid 让 xterm 的 `clientWidth/Height` 自然正确，fit 不需要特判 |
| 最大窗格数 | 4 | 递归任意布局 | Grid 加 `data-panes` 就能覆盖 2/3/4 格，不需要递归容器；再多窗格字体过小，实际没人用 |
| 3 个窗格的排法 | 上二下一（末格横跨整行） | 2×2 留空一格 | 空格会露出容器底色，视觉上像渲染坏了 |
| 布局变更后的尺寸 | 所有窗格统一重新 `fit()` | 只 fit 当前窗格 | 只 fit 焦点窗格会让其他格保持分屏前尺寸，出现文字被裁切（v1.2.0 遗留） |
| 焦点高亮 | `::after` 覆盖层描边 | `inset box-shadow` | xterm 背景不透明，会盖住 inset 阴影（实测看不到） |
| 关闭语义 | 有多个窗格时 `Ctrl+Shift+W` 先关窗格 | 关窗格必须用鼠标 | 与 iTerm 一致，避免误关整个标签 |

同一标签内两个窗格的标签标题：`onTitle` 只在单窗格时生效，否则两个终端会互相覆盖标题（vim/top 会发 OSC 标题序列）。

## 9. 文件在线编辑与续传（v1.3.0）

### 9.1 保存的原子性与冲突

保存走「同目录临时文件 → `fsync` → `rename`」：`rename` 在同一文件系统内是原子的，
所以读者永远看到完整内容，进程被 kill 也不会留下半截文件。临时文件建在目标同目录，
既保证同一文件系统，也保证不越出 `files.root`。权限位从原文件继承（`chmod` 到临时文件），
避免把 0600 的配置写成 0644。

冲突检测用纳秒级 mtime 做乐观锁：

```
打开编辑器 → stat 拿到 version（纳秒 mtime 字符串）
编辑…      → save 带上 version
服务端     → 当前 mtime != version ? 409 冲突 : 原子写入
```

这样「两个人同时编辑」「编辑器开着的时候在终端里 `vi` 改了同一个文件」都不会互相覆盖。
`version` 走字符串是硬约束：纳秒时间戳是 19 位整数，超过 JavaScript 的
`Number.MAX_SAFE_INTEGER`（9007199254740991），JSON 数字在浏览器端会被舍入，
表现为「刚读出来就保存也报冲突」。

### 9.2 断点续传的判定

分块写入接口本身要求 `offset == 当前文件长度`，天然支持续写；难的是判断
「服务端那个半截文件是不是同一个文件的前半段」。做法是读服务端已有内容的前 32KB，
与本地文件同长度前缀逐字节比较：

- 一致 → 从已有长度继续，跳过重复传输
- 不一致 → 说明是同名不同文件，提示覆盖后从 0 重传

只比 32KB 是为了控制成本：真要完全一致才安全，但「前缀相同、后面不同」在实际使用中
基本只出现在文件被截断/修改的场景，此时覆盖确认也会拦住。

## 10. 账号角色与权限（v1.4.0）

### 10.1 能力模型

权限不写成一堆独立开关，而是「角色给默认值 + 逐项覆盖 + 全局闸门取交集」三层：

```
角色默认        perms 覆盖           全局开关
admin     ─┐
operator  ─┼─→  shell / files_*  ─→  取交集  ─→  最终 caps
viewer    ─┘    / records_*
```

`Caps` 是最终结果，随登录响应下发给前端，同时挂在 `auth.Session` 上，每次请求跟着 `call` 走。
校验点只有两类：`handleTermCreate` 看 `Shell`，各文件/录制接口看对应位。

覆盖用三态布尔（`OptBool`）而不是普通 `bool`——必须区分「没写」和「写了 false」：
`perms: { shell: false }` 是「关掉终端、其他照旧」，而普通 `bool` 无法表达未设置。

### 10.2 角色怎么分

| 角色 | 终端 | 文件 | 录制 |
|---|---|---|---|
| `admin` | ✓ | 读/写/删 | 看全部、可删 |
| `operator`（默认） | ✓ | 读/写/删 | 只看自己、可删自己 |
| `viewer` | ✗ | 只读 | 看全部、不可删 |

`viewer` 不是「只读终端」——终端的本质就是执行命令，只读没有意义，所以直接不给终端。
它的用途是审计岗：能翻所有会话回放与文件，但动不了任何东西。

### 10.3 为什么角色在启动时固化

账号表在 `auth.NewManager` 里一次性构建，`Caps` 随 `account` 存下来，请求期只做查表。
好处是热路径零锁竞争、也不会出现「角色被改到一半」的中间态；代价是改配置要重启。
多人系统里角色变更是低频操作，重启成本可以接受。

若将来要做在线改角色，正确做法是给 `account.caps` 加读写锁并让 `Session` 每次取最新值，
而不是把 caps 直接塞进令牌里（那样改权限得等令牌过期）。

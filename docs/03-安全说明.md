# 安全说明

## 1. 威胁模型

| 威胁 | 是否覆盖 | 说明 |
|---|---|---|
| 网络嗅探（同网段抓包） | ✅ | 报文用 SM4-CBC 加密，命令与输出均不可读 |
| 报文篡改 | ✅ | HMAC-SM3 认证，任何字节改动都会失败 |
| 报文重放 | ✅ | 时间戳 ±300s + nonce 去重（会话级 LRU） |
| 暴力破解口令 | ⚠️ 部分 | bcrypt + 失败锁定（默认 5 次 / 10 分钟，按 IP）；无验证码 |
| 中间人替换公钥 | ❌ 未启用 TLS 时 | 应用层无法验证公钥归属，必须靠 TLS 弥补 |
| 拿到网页账号的恶意人员 | ❌ | 等价于拿到该 OS 用户的 shell，这是工具的能力而非缺陷 |
| 浏览器终端 XSS | ✅ 基本覆盖 | 输出经 xterm.js 渲染，不写入 DOM；CSP 限制脚本仅同源 |
| 跨站 WebSocket 劫持 | ✅ | 升级时校验 `Origin` 与 `Host` 一致 |
| 会话令牌泄露 | ⚠️ | 令牌仅在加密载荷内传输，不落 Cookie；存于 `sessionStorage`，随标签页销毁 |
| 日志泄露敏感信息 | ⚠️ | 审计只记事件与主题信息，不记录命令内容与输出 |

## 2. 加密协议

### 2.1 参数

| 项 | 取值 |
|---|---|
| 密钥交换 | SM2（`gmsm` 默认曲线 `sm2p256v1`），密文格式 `04‖C1C3C2` |
| 会话密钥 | 16 字节，浏览器 `crypto.getRandomValues` 生成 |
| 报文加密 | SM4-CBC + PKCS#7，每条报文 16 字节随机 IV |
| 完整性 | HMAC-SM3，32 字节，encrypt-then-MAC |
| 密钥派生 | `encKey = SM3(K‖0x01)[0:16]`，`macKey = SM3(K‖0x02)[0:32]` |
| 防重放 | `ts` 与服务器时间差 ≤ 300s，`nonce` 在会话内 300s 不重复 |

### 2.2 报文格式

```
HTTP body:  {"sid":"<会话ID>","data":"base64(IV‖密文‖MAC)"}
登录 body:  {"sid":"...","k":"<SM2 密文 hex>","data":"base64(IV‖密文‖MAC)"}
明文内容:   {"ts":1700000000,"nonce":"hex","token":"...","p":{...}}
响应:       {"data":"base64(...)"} → {"code":0,"msg":"","data":{...}}
```

### 2.3 实现要点（易踩坑）

1. **SM2 密文的 `04` 前缀**：`gmsm` 的 `Decrypt` 会直接丢弃首字节，要求密文以未压缩点标记 `0x04` 开头；
   而 JS 的 `sm-crypto` 输出不含该前缀。本项目的做法是**协议规定客户端补齐 `04`**，服务端强校验。
2. **HMAC 分组长度**：SM3 的 HMAC 分组为 64 字节，与 SHA-256 相同；浏览器侧自行实现，
   已通过跨语言测试（`test/e2e.mjs`、`internal/crypto/crypto_test.go`）双向验证。
3. **SM4 填充**：统一 PKCS#7，禁止接受零填充，解密后校验填充字节合法性。

## 3. 认证与会话

- 密码使用 bcrypt（cost 10）存储；配置文件写明文时启动即哈希，只保留在内存
- 登录失败按 IP 计数，达到阈值锁定 `login_lock`；用户名不存在也执行一次 bcrypt，降低用户枚举的时序差异
- 令牌 32 字节随机（hex 64 字符），仅存服务端内存，进程重启即失效
- 双超时：空闲 `idle_timeout`（默认 30 分钟）+ 绝对 `session_ttl`（默认 12 小时）
- 并发会话数默认 5，可配置；终端数默认 8（可按账号覆盖）
- **令牌强制**：所有业务接口都必须带登录令牌。`/api/login` 会在**校验密码之前**把会话密钥
  装进通道（它需要密钥才能解密登录报文），所以「握个手 + 故意输错密码」也能得到一个可解密的
  通道。若接口允许空令牌，未登录就能调用文件与终端接口。v1.4.0 起 `openCall` 对空令牌直接返回
  未登录，并补了回归测试
- **权限按账号收敛**：登录响应下发 `caps`，终端创建、文件读写删、录制查看与删除逐项校验；
  前端只是不显示无权限的入口，判定始终在服务端

## 4. 传输通道

- 除 `GET /ws` 外，全部接口为 POST，参数在请求体
- `GET /ws` 是 WebSocket 协议规定的握手方式，无法改为 POST。为降低风险：
  - 票据由 `POST /api/term/ticket` 签发，**一次性、30 秒有效、绑定用户与终端**
  - 升级时校验 `Origin` 与 `Host` 同源
  - 帧内容全部加密
- 若环境要求「绝对不允许 GET/WS」，把 `terminal.transport` 设为 `poll`，全站仅 POST

## 4.1 文件管理的边界

文件管理把「能读写本机文件」这一能力从终端扩展到了网页表单，边界按下面的规则收紧：

| 措施 | 说明 |
|---|---|
| 根目录限制 | 所有路径相对 `files.root` 解析，`..` 在 `path.Clean` 阶段被消掉 |
| 符号链接校验 | 目标路径 `EvalSymlinks` 后必须仍在 root 之下；新建文件校验其父目录 |
| 名称校验 | 重命名只接受单段文件名，拒绝 `/`、`\`、`..`、空名 |
| 权限分级 | 全局 `allow_write` / `allow_delete` 与账号能力取交集：全局关了谁都写不了，账号是 `viewer` 时全局开着也写不了 |
| 上传上限 | `max_upload_mb` 在服务端校验，超限直接拒绝（不依赖前端） |
| 偏移校验 | 分块必须连续，服务端比对当前文件长度，防止乱序拼接 |
| 审计 | 上传/下载/新建/重命名/删除均记录用户、来源 IP、路径 |

仍需注意：登录用户可以在 root 目录内**覆盖已有文件**（前端会二次确认，但不是安全边界），
因此不要把 `files.root` 指向包含系统配置或密钥的目录。

## 4.2 会话录制的边界

- 录制文件包含终端全部输出（可能含敏感信息），默认权限 `0600`，与进程同用户可读
- 录制目录不通过 HTTP 直接暴露，只能经加密接口按 ID 读取；ID 有白名单校验，防路径穿越
- `max_mb` 限制单会话体积，`keep_days` / `max_files` 控制总量，避免磁盘被写满
- 回放的可见范围按角色收敛：`operator` 只列自己创建的会话，`admin` / `viewer` 可看全部；
  读取接口先取元信息判断归属，再读事件，越权请求直接拒绝
- 仍无「按人共享」的概念：能看全部的角色看到的就是全部，需要更细的隔离只能拆成多套实例

## 5. 部署加固清单

- [ ] 配置 `security.ip_whitelist`，只放行运维网段
- [ ] 开启 `tls.enabled`（自签也可，至少避免明文与被动嗅探）
- [ ] 用 `password_hash` 而非明文密码，密码长度 ≥ 16 且不含词典词
- [ ] 以**普通用户**运行（程序默认拒绝 root），该用户只拥有必要权限
- [ ] 调小 `idle_timeout`（如 15m）与 `session_ttl`（如 8h）
- [ ] 定期检查 `data/audit.log`，关注异地/异常时段登录
- [ ] `config.yaml` 权限 600，不放入代码仓库
- [ ] 按需收紧 `files.root`，不需要文件传输时设 `files.enabled: false`
- [ ] 评估录制留存：`record.keep_days`、`record.max_files`，敏感环境可关闭录制
- [ ] 升级前确认无遗留会话，升级后核对 `-version`

## 6. 已知边界

1. **浏览器端密钥在内存中**，本机被控（木马、恶意扩展）时无法防御。
2. **应用层加密不能替代 TLS**：公钥在首次握手时明文下发，中间人可替换。这是协议层限制。
3. **审计不含命令内容**：PTY 模式下命令是逐字符输入的，重建命令需要额外解析，当前版本只记录会话级事件。
   若合规要求「命令级审计」，可后续增加按行捕获（有误判风险）。
4. **不限制可执行命令**：登录即拥有该用户全部能力，包括 `rm -rf`、`bash`、`curl` 外联。
   如需收紧，应通过 OS 层面的权限、SELinux 或容器隔离，而不是依赖本工具的白名单。
5. **无验证码/双因素**：内网场景默认未引入；对高安全要求环境建议叠加 TLS 客户端证书或前置 VPN。
